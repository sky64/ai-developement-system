# 0008: scout64, the Haiku helper for search, reading and summarizing

Date: 2026-11-18. Status: accepted by the owner in the Orca chat of 2026-11-18 (design proposed in full, owner answered the follow-up questions without correction). Implemented by [the scout64 plan](../superpowers/plans/2026-11-18-scout64.md).

## Intent

The owner, 2026-11-18: change the default agent used for search, reading and summarizing to a named helper that runs on Haiku, and send any helper doing simple tasks to it. The ladder (decision 0004) already puts Haiku at rung 0 of the `research` row, but the orchestrator skill sends native read-only subagents to the rung 1 model, Sonnet. Lookups that return facts from files do not need Sonnet. Naming the helper makes it something the owner can keep up with, in the `64` family beside bot64 and crew64-map (decision 0006).

This belongs in crew64, not in Solvela: which model a helper runs on is a dispatch decision, and decision 0004 made crew64 the only chooser. Native subagents run on the owner's Claude subscription directly, not through the gateway, so Solvela is not in their path.

## Goals

- One named agent, `scout64`, shipped by the plugin, on Haiku, read-only, that Claude picks for search, reading, summarizing and lookups in any session where the plugin is enabled.
- Read-only investigation from the orchestrator goes to it by default; escalation climbs to the rung 1 model only when the scout reports it could not answer, and to rung 2 when the question is itself risky-tier.
- A switch and a config entry, so a repo can turn it off or move its rung without editing the agent file.

## Non-goals

- A writing helper. scout64 never edits; anything that writes is still an Orca worker (or, after decision 0009, the orchestrator in native mode).
- Routing scout64 through the gateway. It runs where native subagents run.
- A second helper for summaries that need judgment. The escalation rule covers that.

## Anti-goals

- A scout that guesses. Its prompt makes "could not answer" a first-class result, with what it tried, so the orchestrator escalates instead of acting on a wrong fact.
- A silent downgrade: the status line shows the switch, and the completion report names the model that answered.

## Constraints

- Claude Code agent files take `model: haiku | sonnet | opus | inherit`; the exact model id behind the alias is the harness's current Haiku. The config's `models.research[0]` is reported beside it; when the two name different families the orchestrator reports the deviation, as it does for the ladder.
- Plugin agents surface as `crew64:scout64` wherever the plugin is enabled; the plugin manifest needs no change (agents are discovered from `agents/`).
- Risky tier (orchestrator skill, docs/05, config reader); rung 2; Codex review at effort high; Runtime floor Python 3.13+ and bash on Linux.

## Approaches considered

1. **A plugin agent file with `model: haiku`** (chosen). Named, portable, switchable, and Claude Code's own delegation picks it from its description.
2. **A prose rule: pass `model: haiku` on every read-only Agent call.** Rejected: depends on the orchestrator remembering, gives the helper no name and no tool limits.
3. **A user-level agent in `~/.claude/agents`.** Rejected: not portable, not switchable, and the home-office copy would go stale as the wrapper did.

## Decision

1. **The agent.** `agents/scout64.md`: `name: scout64`, `model: haiku`, `tools: Read, Grep, Glob, Bash`, description: use for search, reading, summarizing, locating code, answering "where is / what does / list all" questions and any other read-only lookup, instead of general-purpose or Explore. Prompt: answer from what you read, cite `file:line`, keep the answer short, never edit or run a command that writes, and when the question needs judgment or the answer is not in the files, reply `could not answer` followed by what you tried.
2. **The switch.** `features.scout64`, boolean, default true. Optional in `check` (a config without it validates and reads as true, like `limits`), so the enabled repos keep working untouched. `CREW64_FEATURE_SCOUT64=on|off` overrides. The status line gains ` scout64=on|off`.
3. **The rule.** Orchestrator skill, Rungs and models: read-only investigation goes to `crew64:scout64` when the switch is on. When the scout replies `could not answer`, re-ask once with a native subagent on the rung 1 model (`sonnet` via the Agent tool's model parameter); a risky-tier question goes to rung 2 directly. With the switch off, today's rule stands: native read-only subagents on the rung 1 model. docs/05's ladder table row for research and read-only subagents names scout64 at rung 0.
4. **The record.** The completion report's "model id actually used" line covers the scout like any worker.
5. **Pins and tests.** `tools/check-ladder-docs.sh` pins the agent's model line, the skill rule and the docs/05 row; `tools/test-crew64-config.sh` covers the switch's default, file value, env override and validation. Plugin version 0.7.0.

## Left to the builder

- Exact description wording that makes Claude Code prefer scout64 over Explore for lookups.
- Whether the scout's Bash allowance needs a stated read-only list in its prompt (the guard still denies writes outside a worktree either way).

## Consequences

- Lookups cost Haiku prices. Summaries that need judgment cost one extra round trip when the scout declines, which is the intended trade.
- The orchestrator's first message shows one more switch. A repo that wants Sonnet lookups sets `features.scout64` to false.
